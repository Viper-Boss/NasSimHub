# 去中心化更新（DHT + NKN）

2026-09-25 定下的方向：更新要去中心化，只用项目自己已有的 DHT 和 NKN 两张网，不另找第三方镜像站（Gitee 之类不做了）。

分两步走：

| 步骤 | 内容 | 状态 |
|---|---|---|
| 第一步 | **签名清单**在网关之间传播：「最新版本是哪个、由哪几个镜像 digest 组成」 | r121 完成 |
| 第二步 | **镜像本身**在网关之间传 | 未开始，开工前要你先定几件事（见最后一节） |

同时定下的另外两件事：
- GitHub 和 jsDelivr 这几个 HTTPS 来源**保留**，和 DHT、NKN 并列。
- 每台网关**默认把自己验证过的更新分享给别的网关**，可以关。

---

## 1. 为什么这样做是安全的

网关**只认签名，不认来源**。清单是发布者用私钥签的，网关用编译进去的公钥验。
所以清单是谁转交的都无所谓：陌生网关、镜像站、U 盘，都是同一种情况。

一个恶意网关最多能做两件事：
- **不回答。** 那就当它不存在。
- **给一份旧的真清单**，想让你停在旧版本。但所有来源一起比，取版本最高的那份，旧的会输给任何一个来源给出的新版本。

它**做不到**的：让网关装上发布者没签过的东西。伪造的清单验签不过，在界面上显示为「签名不对」，不参与比较，也不会被转发给别人。

## 2. 第一步做了什么

### 网关之间怎么问

**NKN**（主力，能穿透路由器）：
- 每一轮最多问 12 台网关：先问你配对过的设备，再从「全网装机名单」里随机抽。全网装机名单就是 NKN 上的 `modemdecknet` 这个 topic。
- 发的是一条很小的询问消息，对方用自己验证过的签名清单回答。
- 只收**这一轮问过的**网关的回答，同一台只算一次。别人主动塞过来的回答直接丢掉，签得再对也不用。
- 后台每 2 小时问一轮，最多等 10 秒。在界面上点「重新检查」也会问一轮，最多等 4 秒，不让页面干等。

**DHT**（libp2p，能直连时用）：
- 新增了一条协议 `/smsbridge/release/1.0.0`，只用来交换这一份签名清单，上限 64 KB。
- 不转发任何别人的流量。这一点和 DHT 原来「不给别人当中转」的规矩是一致的：给出去的是自己验证过的一份文件，不是替别人传东西。
- 问的是当前已经连上的 DHT 节点，也就是局域网里的和配对过的。

### 回答别人（做种）

- 默认开启。「版本与更新」卡片「更新来源」一栏的右下角有开关（分享中 / 未分享）。
- 同一台网关 2 分钟内最多回答一次，全部加起来每分钟最多回答 30 次。
- 只分享自己验证过的清单，一字不改地原样转交。
- 发布者自己的网关从 GitHub 拿到新版本后，会自动转给问它的其他网关。**发布流程不用多做任何事。**

### 界面上看到什么

「更新来源」一栏的 DHT、NKN 两项：

| 显示 | 意思 |
|---|---|
| **N 台网关**（绿色） | 有 N 台网关给出了这个版本的签名清单，并且验签通过 |
| 无应答（灰色） | 问过了，没人回答。早期拿着新版本、又正好在线的网关很少，这是常态，不是故障 |
| 未参与（灰色） | 这台网关这次没在这个网络上问：NKN 或 DHT 关着，或者还没连上 |
| 签名不对 / 格式不对（红色） | 有人给了伪造或损坏的清单，已经被拒绝 |

「N/M 个源给出此版本」和「来源一致」现在把 DHT、NKN 也算进去了。

### 顺手修掉的问题：全网装机名单

之前全网装机名单只认环境变量 `HOMESIM_NKN_SEED`，这个变量只在 190 上手动配过。
结果是**普通安装和发出去的 fpk 都没进名单**，而且名单里的地址和接收消息的地址不是同一个。

现在改成和 NKN 控制通道用同一个身份：每台开着 NKN 的网关都会进名单，名单里的地址就是能收到消息的地址。
（进名单是链上订阅，这个功能本来就是默认开的，只是之前一直没生效。）

### 进程之间怎么接

- **NKN 和 API 在同一个进程里**，由 API 负责发问、收答、回答别人。
- **DHT 在 agent（硬件容器）里**，因为 API 容器没有绑定端口的权限。API 通过 agent 的 `PUT /v1/dht/release`（交出要分享的清单）和 `POST /v1/dht/release/fetch`（向已连接的节点要清单）两个接口使用它。
- **有更新器时，更新渠道在更新器里。** API 把收到的清单交给更新器的 `POST /v1/release/offer`，并从 `GET /v1/release/signed` 取回要分享的那份。更新器会再验一次签。
- **没有更新器时**（比如 190、现在的 fpk），用 API 自己的更新渠道。

关键文件：

| 做什么 | 文件 |
|---|---|
| 问 / 答 / 做种 / 开关 | `internal/httpapi/release_peers.go` |
| 所有来源一起比版本、接收 P2P 来的清单 | `internal/releasechannel/channel.go`（`Offer`、`Signed`） |
| DHT 上的清单协议 | `agent/internal/dht/release.go` |
| 更新器的两个接口 | `internal/ota/http.go`、`internal/updaterclient/client.go` |
| 卡片 | `web/src/components/SoftwareUpdateCard.vue`、`web/src/state/softwareUpdate.ts` |

## 3. 第一步的局限（如实说）

- **早期基本没人能回答。** 只有已经升到 r121 这版的网关才会回答别人。第一批用户升级之前，DHT 和 NKN 两项大多显示「无应答」，这很正常。
- **DHT 只能问到局域网和配对的设备。** 项目没有公共引导节点。要让 DHT 连到陌生网关，就得把自己的 IP 地址发布出去，这是第二步要你定的事。
- **镜像还是从 ghcr（或你配的国内镜像站）拉。** 所以连不上 ghcr 的网关，现在能**知道**有新版本，但还**下载不了**。

## 4. 第二步（镜像走 P2P）开工前要你定的事

大致做法：
1. CI 额外把每个镜像打成一个打包文件，按 1 MB 分块，每块算哈希；块哈希列表的哈希写进签名清单。清单格式要升一版。
2. 网关之间按块互传，每一块单独校验，所以可以同时从很多台陌生网关各拿几块。
3. 能直连走 DHT，连不上走 NKN 会话。
4. 上传限速，默认比如 1 MB/s。
5. 全部下完、校验通过后，更新器用 `docker load` 导入，再按清单里的 digest 核对。

要你定的：
1. **要不要让网关之间直连？** 直连快得多，但对方会知道你的公网 IP。不直连就只走 NKN，全程不暴露 IP，但速度慢很多。
2. **做种占多少硬盘？** 要分享镜像，就得把打包文件留在盘上，每个版本几百 MB。建议只留最新一个版本，可以关。
3. **默认上传限速多少？**

另外有一个技术点要先在真机上验证：`docker load` 导入的镜像，能不能和清单里的 registry digest 对上。Docker 29 默认用 containerd 存镜像，这一点可能和老版本不一样。
